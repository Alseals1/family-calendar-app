## 3. Architecture

```
Browser (React client components: calendar, forms)
   │  supabase-js with the user's session (anon key + JWT)
   ▼
Next.js on Vercel
   ├─ middleware: refresh session, redirect unauthenticated users
   ├─ Server Components: load data with the user's session (RLS applies)
   └─ Server Actions: zod validation → Supabase calls with the user's session
   ▼
Supabase
   ├─ Auth (email + password, password reset)
   ├─ Postgres with RLS on every table   ← the real security boundary
   ├─ RPC functions (security definer) for multi-step writes: create_family,
   │  create_invitation, accept_invitation, remove_member, leave_family
   └─ Storage bucket `avatars` with RLS
```

Rules:
- The app **never** uses the service-role key. Every query runs as the signed-in user, so RLS covers everything. Auth emails are sent by Supabase itself through Resend SMTP (configured in the Supabase dashboard), so the app holds no email secret (D-02).
- Validation happens three times: zod in the form, zod in the server action, constraints in Postgres.
- Calendar rendering runs in client components so dates use the browser's time zone. The server stores and compares UTC only.

## 4. Database

All primary keys are `uuid default gen_random_uuid()`. All timestamps are `timestamptz`. `updated_at` is set by a trigger.

### Tables

**profiles** — one per auth user, created by a trigger on `auth.users` insert.
- `id uuid pk references auth.users on delete cascade`, `full_name text not null` (1–100 chars), `avatar_url text`, `created_at`, `updated_at`.

**families**
- `id`, `name text not null` (1–80), `created_by uuid not null references profiles` (= owner), `created_at`, `updated_at`.

**family_members**
- `id`, `family_id → families on delete cascade`, `user_id → profiles null`, `member_name text not null` (1–80), `member_type text check in ('adult','child')`, `calendar_color text check ~ '^#[0-9a-f]{6}$'`, `avatar_url text`, `created_at`, `updated_at`.
- Check: `(member_type = 'adult') = (user_id is not null)`.
- Unique `(family_id, user_id)`; unique `(user_id)` where not null (D-06); unique `(id, family_id)` for composite FKs.
- Adult count per family ≤ `max_adults` (2), enforced inside the RPCs.

**family_invitations**
- `id`, `family_id`, `invited_email citext not null`, `invited_by → profiles`, `invitation_token_hash text unique not null` (SHA-256 of the token; the raw token is only in the link), `status text check in ('pending','accepted','revoked','expired')`, `expires_at timestamptz default now() + interval '7 days'`, `accepted_at`, `created_at`.
- Unique pending invite per `(family_id, invited_email)`.
- Note: the spec names the column `invitation_token`. Storing a hash instead means a database leak does not expose usable invite links.

**events**
- `id`, `family_id`, `created_by → profiles`, `title text not null` (1–200), `description` (≤ 5000), `location` (≤ 300), `start_time timestamptz not null`, `end_time timestamptz not null`, `is_all_day bool default false`, `visibility text check in ('private','shared','family')`, `calendar_type text check in ('personal','family')`, `created_at`, `updated_at`.
- Check `end_time > start_time`.
- Check `(visibility = 'family') = (calendar_type = 'family')` (D-07).
- Check for all-day: start and end at 00:00 UTC (D-08).
- Unique `(id, family_id)` for composite FKs.
- Trigger: `created_by` and `family_id` cannot change on update.
- Indexes: `(family_id, start_time)`, `(family_id, end_time)`, `(created_by)`.

**event_assignments**
- `id`, `event_id`, `family_member_id`, `family_id`.
- Composite FKs `(event_id, family_id) → events(id, family_id) on delete cascade` and `(family_member_id, family_id) → family_members(id, family_id) on delete cascade`, so an event can only be assigned to members of its own family. (`family_id` is an addition to the spec's columns for this reason.)
- Unique `(event_id, family_member_id)`. Index on `family_member_id`.

### Helper functions (security definer, `search_path = ''`, stable)
- `is_family_adult(fid uuid) → bool` — the caller is an adult member of `fid`.
- `is_family_owner(fid uuid) → bool`.
- `my_family_id() → uuid`.

These avoid recursive RLS on `family_members`.
They live in the `private` schema: `authenticated` may use it and execute these three helpers only, and the API does not expose it, so they are not RPCs.

### RLS policies (summary)

| Table | select | insert | update | delete |
| --- | --- | --- | --- | --- |
| profiles | self, or shares a family with me | trigger only | self | — (cascade from auth) |
| families | `is_family_adult(id)` | via `create_family` RPC | owner | owner |
| family_members | `is_family_adult(family_id)` | children: any adult of the family; adults: RPCs only | children: any adult; adult row: that adult | children: any adult; adults: `remove_member` / `leave_family` RPCs |
| family_invitations | adults of the family | via `create_invitation` RPC | revoke: adults of the family | — |
| events | `is_family_adult(family_id) and (created_by = auth.uid() or visibility <> 'private')` | `created_by = auth.uid() and is_family_adult(family_id)` | creator; any adult of the family for `family` events (D-03) | same as update |
| event_assignments | `exists (select 1 from events where id = event_id)` (inherits the events policy, so private assignments stay hidden) | caller can update the event | — | caller can update the event |
| storage `avatars` | family adults | path prefix = own family id | same | same |

Update is column-limited for `authenticated` (anon has none): profiles `full_name`, `avatar_url`; families `name`; family_members `member_name`, `calendar_color`, `avatar_url`; family_invitations `status`. So use `update` with explicit columns on these tables, not supabase-js `upsert`. Avatar paths are `<family_id>/<file>` in the private `avatars` bucket (1 MiB, jpeg/png/webp).

### RPCs
- `create_family(name, display_name, color) → family_id`: refuses if the caller already has a family.
- `create_invitation(email) → raw_token`: caller must be an adult; refuses if the family is full or the email is already a member.
- `accept_invitation(token)`: checks hash, `pending`, not expired, `invited_email = auth.email()`, caller has no family, family not full; inserts the adult member; marks the invite `accepted`.
- `remove_member(member_id)`, `leave_family()`: apply D-05, including deleting the leaving adult's private/shared events in that family.

## 5. Calendar logic (pure, unit-tested)
- `getVisibleRange(view, anchorDate, weekStartsOn)` → the start/end of the month grid, week, or agenda window (agenda = 30 days from anchor).
- Query: events overlapping the range: `start_time < rangeEnd and end_time > rangeStart`.
- `applyScope(events, scope, me)`: My / Family / All visible (PRD CAL-4).
- `applyMemberFilter(events, selectedMemberIds)`.
- `eventColor(event, members)` and `readableTextColor(bg)` (WCAG contrast).
- `defaultEventTimes(now)`: round up to the next 30 minutes, +1 hour.
- `toAllDayRange(startDate, endDate)` / `fromAllDayRange(...)`.
- Multi-day events appear on each day they cover.

## 6. Testing strategy (TDD)

Every task follows **red → green → refactor**, and every PR shows it:

1. **Red**: write the failing tests first and commit them (`test: ...`). For DB work that means a pgTAP file; for logic, a Vitest file; for a user flow, a Playwright spec.
2. **Green**: write the least code that passes. Commit (`feat: ...`).
3. **Refactor** with the tests green.
4. **E2E**: each user-facing task adds or extends a Playwright spec for its flow, run at desktop and phone sizes.
5. Before a PR: `npm run lint`, `npm run typecheck`, `npm test`, `npm run test:db`, `npm run test:e2e` all pass.

| Level | Tool | Command | Covers |
| --- | --- | --- | --- |
| Unit | Vitest | `npm test` | dates, validation, scope/filter, colors |
| Component | Vitest + RTL | `npm test` | event form, calendar views, visibility select |
| Database / RLS | pgTAP | `npm run test:db` | constraints, triggers, every RLS policy, RPCs, the privacy scenarios |
| API-level privacy | Vitest + supabase-js against local Supabase | `npm run test:integration` | user B with a real JWT tries to read/modify user A's private event through the REST API |
| End-to-end | Playwright | `npm run test:e2e` | every PRD flow; two browser contexts for the spouse flows; Mailpit for invite/reset emails |

Test data is always made up (`alex@example.test`, `sam@example.test`). Tests never run against a hosted Supabase project.
